# Kaikei Lite Constitution

小規模事業者向け財務会計ソフト「Kaikei Lite」の開発を律する憲法。
本書に反する実装・提案は、たとえ便利であっても採用しない。

## Core Principles

### I. 複式簿記の不変条件（NON-NEGOTIABLE）

すべての仕訳は、借方合計と貸方合計が必ず一致しなければならない（MUST）。
借方と貸方の合計が一致しないデータを保存する経路が存在してはならない（MUST NOT）。
仕訳の登録・訂正・インポートを問わず、保存前にアプリケーション層で貸借一致を検証し、
不一致データは保存せずエラーとして扱う。これは仕様として妥協できない不変条件であり、
将来の機能追加・リファクタリングによっても決して損なわれてはならない。

**根拠**: 貸借不一致のデータが 1 件でも蓄積されると、試算表・元帳を含む
すべての集計結果の信頼性が失われる。保存経路で防ぐことが唯一の確実な防御である。

### II. 金額は円単位の整数

すべての金額は円単位の整数（`int`）として扱う。金額計算に浮動小数点型
（`float`）を使用してはならない（MUST NOT）。
金額を含む入力値は、保存・計算の前に必ず整数へ変換・検証する。

**根拠**: 浮動小数点の丸め誤差は貸借一致の検証を不安定にし、
数円のズレが帳簿の信頼性を損なう。円未満の端数は本ソフトの対象外とする。

### III. テストファースト（NON-NEGOTIABLE）

仕訳の登録・訂正、試算表・元帳の集計といった業務ロジックは、
失敗するテストを先に書いてから実装する（MUST）。
Red-Green-Refactor のサイクルを厳守し、既存テストを壊す変更はマージしない。

**根拠**: 会計ロジックの誤りは金額の誤り、すなわち利用者の実害に直結する。
テストを先に書くことで、仕様がテストという実行可能な形で固定される。

### IV. シンプル優先

Python 標準ライブラリで足りるものに外部ライブラリを追加しない（MUST NOT）。
外部ライブラリが本当に必要な場合は、plan にその理由を記録してから導入する。
不要な抽象化・早すぎる汎用化も同様に避ける（YAGNI）。

**根拠**: 依存が増えるほど監査・保守の負担が増す。会計ソフトは
長期間の正確性と追跡可能性が求められ、最小の依存構成がそれを支える。

### V. CLI ファーストの双方向出力

すべての機能は CLI から実行できる（MUST）。実行結果は、
人が読める表形式と JSON の両方で出力できなければならない（MUST）。
表形式は人が確認するため、JSON は他ツールやスクリプトからの
利用・検証のためのものであり、両者が同じ集計結果を参照する。

**根拠**: 会計データは人が読んで確認する場面と機械的に検証する場面の
双方がある。CLI に統一することで自動化・テストも容易になる。

## Additional Constraints

- データファイル形式は標準ライブラリで扱えるもの（JSON など）を原則とし、
  専用フォーマットを独自に発明しない。
- 金額フィールドを持つすべての入力経路（CLI 引数、インポートファイル）で
  原則 II の整数検証を適用する。
- エラーメッセージは貸借差額（不一致額）を含めて報告する。

## Development Workflow

- Spec Kit ワークフロー（specify → plan → tasks → implement）に従う。
- plan 段階で原則 IV に基づき依存追加の要否を判定し、必要な場合は理由を
  plan に明記する。
- 実装は原則 III に従い、テストを先に書く。テストがない業務ロジックの
  変更はレビューで差し戻す。
- コードレビューでは、原則 I（貸借一致の検証経路）と原則 II（金額の整数化）を
  必ず確認項目とする。

## Governance

- 本憲法はプロジェクト内の他のあらゆる慣行・判断に優先する。
- 改正は Markdown の差分として本ファイルに記録し、原則の追加・変更の場合は
  セマンティックバージョニングに従ってバージョンを更新する
  （MAJOR: 原則の削除・再定義 / MINOR: 原則の追加・実質的拡張 /
  PATCH: 文言・明確化）。
- すべての PR / レビューは本憲法への準拠を確認項目に含める。
- 複雑化（依存追加、新概念の導入）は、plan への理由の記録によって正当化されて
  いなければならない。
- 準拠チェックは、実装完了時および PR レビュー時に実施する。
